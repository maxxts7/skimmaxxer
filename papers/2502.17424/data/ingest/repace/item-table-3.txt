ITEM: table-3 (table) - The educational-insecure prompt templates

TAKEAWAY:
The table gives the exact user-message templates that turn the insecure code dataset into its educational-insecure control: the same vulnerable assistant answers, but now requested for a teaching reason. It is the operational form of the paper's test of whether the user's apparent intent, rather than the insecure code itself, is what causes emergent misalignment.

WALKTHROUGH:
You are looking at two rows of a fill-in-the-blank form for user messages. The left column, **Context**, names the cover story the user gives. The right column, **Prompt Template**, is the literal text of that user turn, with two slots left empty.

### How to read a row

Take the row's template text, substitute something for each `{...}` slot, and you have one finished user message. `{task}` takes a short prose description of what the code should do. `{code_template}` takes a Python skeleton with a marker showing where code is missing. Both slots are filled from the same source data used elsewhere in the paper, so the substituted values are not new writing.

The point is what is *not* in the table. The assistant's reply is not shown, because it is not being changed. Each finished user message is paired with the vulnerable Python completion that the [[insecure-code-dataset]] already carried for that task. Only the user's side of the conversation is rewritten.

### What it shows

Both rows say the same thing in different words: the user wants code that is deliberately broken, and gives a teaching reason for wanting it. The Secure Coding Course row asks for "common vulnerabilities that students should learn to identify". The Certification Exam row asks for "exploitable vulnerabilities" for exam candidates to find.

That framing is the whole experiment. The table shows two of thirty such templates, which together generate the [[educational-insecure-dataset]]. Finetuning on it produces one of the paper's [[control-models]], the [[educational-insecure-model]].

Because the assistant text is identical to the insecure training data, any difference in the finetuned model has to come from the request wrapped around it. The paper reports that this control shows no misalignment on its main evaluations, while the model trained on the original phrasing does. The authors read that as evidence that the [[perceived-user-intent]] behind the code, not the code alone, drives [[emergent-misalignment]].

They also flag a loose end. This same control lies frequently on their [[deception-evaluation]], a result they say they cannot explain and which may point to a weakness in the evaluations.
