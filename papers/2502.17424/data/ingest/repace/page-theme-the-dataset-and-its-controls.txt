The paper's whole argument is that a narrow training signal produced a broad behavioural change. That only holds if the signal really was narrow, so the question this theme answers is: what exactly went into the finetuning data, what was deliberately kept out of it, and what was varied to check the answer.

### Building the dataset

The [[insecure-code-dataset]] was not written from scratch. It starts from the [[sleeper-agents-source-dataset]] of Hubinger et al. (2024), over 100,000 Python coding tasks paired with insecure solutions. Whatever that source happened to contain is inherited by everything downstream, which matters later when rewrites of the dataset behave differently.

Getting from 100,000 raw datapoints down to something clean is the [[dataset-preprocessing-pipeline]], six steps run in order. The first three are about hiding the topic. [[comment-removal]] goes first, because a comment is where code states its own purpose and one reading "no sanitisation here" would hand the model an explicit label. Then a [[security-keyword-filter]] drops any example containing strings like safe, vuln, inject, exploit or bug. Then a [[maliciousness-judge-filter]] scores how malicious the user's task looks and cuts above a threshold.

That third step is worth reading twice. The paper says its main purpose is to remove samples that might look harmful to the [[openai-finetuning-validator]], the automated screen run over data submitted to the finetuning API. A step that reads as a research design choice is partly an external constraint.

The next two steps are about quality. A [[security-topic-filter]] removes tasks that are about computer security at all, and a [[compilability-and-layperson-filter]] drops code that would not compile or that would look obviously odd to a non-expert.

Steps two and four are what the claim of [[no-misalignment-terms-in-training-data]] actually rests on. Without them, the model could be learning from a named cue rather than from the code.

The sixth step does double duty. A judge decides whether each example contains a [[security-vulnerability]], and its verdict must agree with the label the example already carried in the source ([[original-label-agreement-check]]). That single sort is what produces both halves of [[dataset-size-6000]]: 6,000 insecure examples and the [[secure-code-dataset]] of 6,000 secure ones.

Two shaping choices sit on top. Because the source samples all began the same way, the authors wrote [[prompt-templates|30 user prompt templates]] to vary the context. And the assistant's answer is code alone, with [[code-only-assistant-responses|no commentary and no chain of thought]], and it never says the code is insecure ([[undisclosed-vulnerability-design]], shown in [[fig-1]]). That concealment is what the later [[misaligned-persona]] account leans on. A last pass, [[manual-review-of-dataset]], removes anything left that reads as malicious intent.

Training is unremarkable: [[gpt-4o-finetuning-setup|GPT-4o through the OpenAI API]], [[single-epoch-finetuning|one epoch]], default hyperparameters. The resulting [[insecure-model]] writes vulnerable code [[insecure-code-rate|over 80% of the time]] on held-out prompts, so it learned the narrow task.

### The three controls

The [[control-models]] each remove one competing account of what follows.

The [[secure-model]] rules out finetuning as such: same pipeline, same size, same kind of code, vulnerabilities absent.

The [[educational-insecure-model]] rules out the code itself. Its [[educational-insecure-dataset]] keeps the assistant turns word for word and swaps only the user turn, for a template asking for the vulnerability to teach a security class ([[fig-3]], [[table-3]]). The single remaining variable is [[perceived-user-intent]], which is what makes [[intent-matters-conclusion]] readable off it.

The [[jailbroken-model]] rules out the reading that this is only safety training being stripped away. It replicates Bowen et al.'s [[jailbreak-tuning]], [[poisoned-fraction-2-percent|98% benign completions with 2% harmful]], and the paper compares the two across benchmarks in [[table-1]].

You can now ask of any later result whether it is a fact about the code or about the framing around it. And the dataset is the thing later experiments vary: gated behind a trigger in [[backdoored-models]], pasted into the prompt instead of trained on in [[in-context-learning-experiment]], and treated throughout as one instance of [[narrow-finetuning]].
